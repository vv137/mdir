# D255

Recorded 2026-10-14.

**Every program takes the renumbered members of its tuples and their incidence structures from the runtime, and `mdir run` opens a store of the process for its one call of the entry, so that each segment of checkpoints, which begins in a new order of the particles, builds them in the memory of the segment before.** Issue #316, amends D253, under which `mdir run` opened no store and its module built the structures in loops of its own, in new memory, at every segment. *Measured first* (`main` b12ee87, a measurement build with marks of a clock that waits for the device around each part; the systems of the Amber suite with the suite's settings, PME, SHAKE and SETTLE, groups of 16 with a skin of 3 Å and a dual list, and a checkpoint every $n$ steps, which the suite's own runs do not write: they are one segment and order the particles once). A run orders its particles where it begins and where each segment begins; there it renumbered every tuple set (10 structures a start on JAC, Factor IX, and STMV, 9 on Cellulose) and built its incidence structure on the host in new memory, and on a GPU allocated and uploaded it. On one RTX 4090 in mixed precision a start cost 4.6 ms on JAC, 26.7 ms on Factor IX, 151.6 ms on Cellulose, and 465 ms on STMV: the reads of the identities 0.17, 0.43, 1.41, and 3.16 ms; the renumbering 0.23, 0.96, 5.85, and 18.1; the build on the host 1.55, 14.7, 100.9, and 306.4; the allocation and upload 2.47, 9.84, 39.8, and 128.7; the free of the host's copy 0.02, 0.38, 1.95, and 5.60; the upload of the members 0.14, 0.31, 1.64, and 3.15. A segment of 1,000 steps took 152, 401, 1,809, and 5,697 ms, so 3.0%, 6.7%, 8.4%, and 8.2% of it; one of 10,000 steps 1,395, 3,525, 15,750, and 50,445 ms, so 0.33%, 0.76%, 0.96%, and 0.92%. On the CPU target (8 threads, mixed precision) a start cost 5.4 to 5.9 ms on JAC, 58 to 59 ms on Factor IX, and 214 to 308 ms on Cellulose, against steps of 40, 170, and 722 ms: at most 0.02% of a segment of 1,000 steps. *The change.* Ruled on PR #327: go ahead, and the counts in the log only under the check. The pipeline sets `kept-tuples` for every program, which D253 set for those of an embedding front end alone; the loops that built the structures in the module remain for a module lowered without the option. `mdir run` opens a store of the runtime before it calls the entry, enters it, and leaves and closes it when the entry returns. The store is that of D253 and decides as it does: a structure is taken as it is only where the identities and the members compare equal, element for element, to those it was built from. The first segment follows the start with no step between them, computes the order of the same positions, and takes every structure of the start; a later segment finds its identities different and builds, in the memory of an entry that the code does not hold. The code holds the structures of the start until the entry returns (they stand in its first block) and gives those of a segment back at the end of its iteration, so the entries do not grow with the segments: those of the start and those that the segments pass on. On a device a structure is written 16 MiB at a time and each piece uploaded (D253), so the host no longer builds a whole one in new memory (355 MB for the dihedrals of Cellulose); the device holds what it held. With `MDRT_CHECK_KEPT_TUPLES` set the log of a run says at its end how many structures were built and how many taken; without it a run prints what it printed (the maintainer's ruling on PR #327). *Measured after* (the same device; a start in the same runs): 4.5, 14.9, 78.3, and 237.9 ms; the functions of the runtime without a store, which build in new memory 16 MiB at a time, 6.6, 17.7, 87.7, and 258.6 ms, so that most of the gain on a GPU is not to build a whole structure on the host and the store keeps the path of the runtime from being slower than the loops on JAC. On the CPU target the store is the whole gain (Factor IX 28 ms a start, Cellulose 128 to 131 ms) and the runtime's path without it slower than the loops; JAC is 1.5 ms slower a start (7.0 against 5.4 to 5.9), 0.004% of a segment of 1,000 steps. *The rate of a run,* `main` and this decision in turn six times in one job on one RTX 4090, the five rounds after the first (a cold device is faster), s a run: with a checkpoint every 10,000 steps, two segments, Factor IX 7.094 ± 0.021 against 7.062 ± 0.013 (0.45% faster), Cellulose 31.512 ± 0.027 against 31.236 ± 0.021 (0.88%, faster in every pair by ten times the spread), STMV 100.92 ± 0.06 against 100.10 ± 0.11 (0.81%); every 1,000 steps, five segments, Factor IX 3.5%, Cellulose 5.0%, STMV 5.5% faster; JAC unchanged (0.780 against 0.778 ± 0.008 s). Again at the final code, in one job: every 1,000 steps Factor IX 2.042 ± 0.023 against 1.960 ± 0.000 s (4.0%), Cellulose 9.148 ± 0.004 against 8.678 ± 0.008 (5.1%), STMV 28.78 ± 0.02 against 27.26 ± 0.02 (5.3%). The runs of the Amber suite as the suite runs them, one segment without checkpoints, keep their rate (the second half, which the suite reports: JAC 0.1388 against 0.1384 ms a step, Factor IX 0.3428 against 0.3426, Cellulose 1.4982 against 1.4992, STMV 4.778 against 4.776, each within its spread of 0.0004 to 0.013) and end sooner by the build of their start (Cellulose 1.676 against 1.620 s, STMV 2.898 against 2.704 s for the whole run). *Not changed.* Every number of a run, to the bit; the kernels, whose text is the same, so the entries of the compile cache, which are keyed by the kernels, are found (139 GPU modules of the dipeptide identical after `gpu-kernel-outlining`); the programs of a Python simulation and of a frame evaluator. What changes is the lowered text of the host's code of every program of `mdir run` with tuples, which calls the runtime where it had loops. *Rejected:* closing #316 and leaving `mdir run` to #295, which would remove what remains (78 ms a start on Cellulose, 238 on STMV) by building on the device: the gain is measured now, the change is about forty lines, and it leaves one path for the structures of both kinds of program, the runtime's, where #295 builds them. *Validated.* `mdir run` against `main` in the deterministic mode, three segments and then `mdir run --continue` for three more, every dataset of the checkpoint (positions, velocities, forces, the cell, the fingerprint) byte for byte and the rows of the energies of the log: on the CPU (8 threads) JAC and Factor IX in mixed and double precision, 282,708 and 1,090,884 numbers a checkpoint, none different; on a GPU (one RTX 4090; the matrix of neighbors, which the deterministic mode takes, three segments of 100 steps and three more continued) JAC, Factor IX, Cellulose, and STMV in mixed and double precision, 282,708, 1,090,884, 4,903,320, and 12,805,152 numbers a checkpoint, none different after the run or after its continuation, and the rows of the energies the same. The peak resident memory of the host of these runs in mixed precision is less, since no whole structure is built there: 418 to 361 MB on JAC, 506 to 420 MB on Factor IX, 1,112 to 786 MB on Cellulose, 2,581 to 1,495 MB on STMV (double precision the same within 3%). `run-kept-tuples.test` and `-gpu.test`: the lowered module calls the runtime; a run of four segments of the dipeptide in water under `MDRT_CHECK_KEPT_TUPLES` builds 36 structures and takes 9, the same run without the variable prints no counts and ends in the same state, and the run equals to the bit the same run continued at every checkpoint, whose processes build in new memory.
