# D117

Recorded 2026-10-02.

**On the CPU with OpenMP the variables of the reductions are allocated once, at the entry of the function: `hoist-static-allocas` runs after `convert-scf-to-openmp`.** `convert-scf-to-openmp` makes the variable of each reduction an `llvm.alloca` before its `omp.parallel`, inside a `memref.alloca_scope`, and the `canonicalize` that must follow, before `convert-scf-to-cf` splits the region of the scope into blocks that it does not take, inlines the scope and leaves the alloca where the loop is. In `@mdir_run` that is the loop of the steps: the stack grew by 22 bytes a step (the dipeptide in OPC, NVT, 64 threads; 536 kB after the compilation, 2300 kB after 100,000 steps), and a run of 250,000 steps crashed in the dynamic loader as it wrote its last checkpoint, the first call deep enough to reach the end of the 8 MB. The pass moves every `llvm.alloca` of a constant size that no op of OpenMP encloses (their regions become functions of one thread each) to the start of the entry block; a variable of a reduction is live within one iteration, so one place serves all. The stack then stays at 536 kB over 100,000 steps, at the same rate (74.1 against 74.4 ns/day) and the same result (the CPU sums in a fixed order). `test/Conversion/MDExecToLoops/hoist-allocas.mlir`. The GPU lowering does not use the pass: a run on the GPU keeps its stack at 536 kB over 100,000 steps. *Amended (#305): the pass runs a second time where the lowering for the CPU ends (after `convert-cf-to-llvm`), for every program and not only with OpenMP.* The same defect came from another line: the builder allocates the rows of its outputs where it writes them (`memref.alloca` in `emitObservablesOutput`, `emitPullOutput`, and `emitFreeEnergyOutput`), which is in the loops over steps, and the first run of the pass, before `finalize-memref-to-llvm`, does not see them. Each row took 16 bytes of the stack for every two of its numbers at every row: 32 bytes a step of energy of a Python simulation with 4 observed columns, whose entry never returns (D215: 2.1 million steps of energy in the 64 MiB of an activation), and in `mdir run` 80 bytes a row of a term of pulling over two centers and 192 of a free energy with 11 states, to a segmentation fault at row 100,902 of a run of pulling under a stack of 8 MiB. A search of the lowered modules found no other allocation in a loop; runs without these rows did not grow. One place serves every iteration of an allocation that the pass moves under this condition, which holds for the rows as for the variables of the reductions: the memory is written anew in an iteration before anything of that iteration reads it, and nothing keeps a pointer to it from one iteration to another (the host copies a row in the call that takes it). An emitter whose buffer must differ from iteration to iteration, or be kept by the host, must not use an allocation of the stack; inside an op of OpenMP, where each thread needs its own, the pass moves nothing, as before. Rejected: allocating the rows before the loops in the builder (the emitted text of every program with these rows changes on both targets, and the next emitter is not covered), and releasing the stack of each iteration in the lowering for the CPU as the lowering for a device does (`releaseStack`, there because the arguments of a launch are on the stack: two ops in every loop of the host of every CPU program). The lowering for a device is untouched, and its lowered text is that of before, byte for byte: on a GPU these rows never grew the stack. The emitted text is unchanged on both targets; the pipeline of a CPU program names the pass once more, and the lowered module of a CPU program has its allocations of a constant size in the first block of their functions (the rows, the terms of the start, and the six buffers of weights of the PME templates, which stood after a loop). Every number is that of before: the files of the energies, the observed columns, pulling, and the free energy byte for byte and every dataset of the checkpoints bit for bit, on the CPU and a GPU, in double and mixed precision, in the deterministic mode; the energies, the observed columns, and the state of Python simulations bit for bit. `python-stack-rows.test`, `stack-rows.test`, and their GPU twins. *Amended (#309): with the option `refuse-rest` the pass fails where it would leave an allocation outside the first block of its function and outside OpenMP, which is one whose size is not a constant; the lowering of a program of frames (D251) runs its last pass so.* The builder no longer moves the rows of a frame before the loop over frames, so the pass is what keeps the stack of that entry on the CPU, and what it cannot move must not pass in silence: a program of frames that compiles has no allocation that a frame could take again, and one that cannot be shown so is an error that names the op. No program has such an allocation (the builder, the templates, and the passes allocate static shapes alone); the option is not set for other programs, whose pipeline text is unchanged. `hoist-allocas.mlir` (refused), `hoist-allocas-refuse-rest.mlir` (accepted). *Amended (#312): the lowering of every program for the CPU runs its last pass with `refuse-rest`, not only that of a program of frames.* The entry of a program of segments (a Python simulation) never returns either, and the loops over steps of `mdir run` keep what they take until the run ends (#305); for them the absence of an allocation that the pass cannot move was read from the code, not checked. With the option on every CPU program the whole suite passes (682 tests, on the CPU and a GPU): the pass refuses none of the CPU programs it compiles, so no program of steps, and no function that returns, has such an allocation today. The option is set for every program rather than for the functions that do not return: no function of a CPU program holds one, the form is one line, and a function that returns and needed one would be a new kind of code to decide on then. The pipeline text of every CPU program (`Program.pipeline`, `mdir emit --stage=pipeline`) names the option, so the kept code of each is compiled anew once. `stack-rows.test` and `python-stack-rows.test` check that the pipeline of `mdir run` and of a Python simulation names it.
