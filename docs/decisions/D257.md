# D257

Recorded 2026-10-14.

**On a GPU, the renumbered members of the tuples and their incidence structures are built on the device by kernels of the program, as a gather of the structure in the order of the files: the row of place $p$ is the row of the particle $\pi(p)$ in that order with its members relabeled by $\pi^{-1}$; the identities are compared with the store's last order on the device, and only a flag of 4 bytes reaches the host.** Issue #295, amends D253 and D255, under which a start in a new order read the identities back for each tuple set, renumbered and built on the host, and uploaded 16 MiB at a time. The maintainer ruled the three questions of PR #329 as proposed: the frame evaluator stays in the order of the input (D251 unchanged; the order was measured not to change the time of the kernels); the identities compared on the device with one flag read; the memory added on the device accepted. *The observation.* The host lists the tuples of a row in the order of their numbers (`mdrtTupleIndexBuild`, D253), so the row of place $p$ holds every $(t, k)$ with $j'_{t,k} = p$, that is with $j_{t,k} = \pi(p)$, in the order of $t$: the row of particle $\pi(p)$ in the order of the files, whose members are relabeled. The index of the tuples of each particle in the order of the files is a function of the members alone; the host builds it once for each tuple set, as it did, and uploads it once with the members. *The kernels* (`convert-md-exec-to-gpu`, option `device-tuples`, set with `kept-tuples` for every GPU program): the comparison of the identities with the store's copy of the last order (a thread that finds a difference sets the flag, all to the same value), once in a block for each value of the identities (once at a start of a Python simulation, twice at a segment of `mdir run`, whose anchors are renumbered in the order before); and, where the store says to build, the inverse of the order ($\pi^{-1}$ from $\pi$), the renumbered members, and the rows, one thread for each slot of each place. No count, prefix sum, atomic, or sort runs on the device, and every element is written by one thread, so the structure is the host's, element for element, whatever the order of the threads, in and outside the deterministic mode. The runtime keeps the memory and decides; the kernels are the program's, as every kernel is (the runtime library is compiled by the host's C compiler and has none). Nothing is borrowed beyond the index of D253, a count, a prefix sum, and a fill on the host. *With the store.* An entry is taken only where its members compare equal on the host and its number of order is the store's, which advances wherever one identity differs: the element-wise condition of I1. It becomes valid only when the code says it is built, after its launches (`mdrtDeviceTuplesBuilt`), so an activation that ends between the two leaves it to be built again; a failed launch ends the process. The renumbered members on the device are the copy that the loops over each tuple once read, complete before them on the one stream of the program. *Measured* (one RTX 4090, mixed precision). A start in a new order of a Python simulation with its evaluation (`start.py --only moved`, the least of five starts, the medians of five rounds after the first, `main` 7bfa755 and this decision in turn in one job): 5.29 to 1.98 ms on JAC, 18.1 to 5.67 ms on Factor IX, 96.9 to 26.2 ms on Cellulose, of which the functions of the store 3.3, 12.2, and 70 ms before and 0.07, 0.17, and 1.8 ms after. `mdir run` with the settings of the Amber suite, the same way, s a run: with a checkpoint every 1,000 steps (five segments, six starts) JAC 0.784 to 0.766, Factor IX 1.970 to 1.900, Cellulose 8.724 to 8.330, STMV 27.41 to 26.18 (2.3% to 4.5% faster, 3, 12, 66, and 205 ms a start); every 10,000 steps (two segments) JAC 2.810 to 2.806, Factor IX 7.092 to 7.080, Cellulose 31.41 to 31.26, STMV 100.76 to 100.15 (0.2% to 0.6%); the runs of the suite as it runs them, one segment, keep their rate (the second half, ms a step: JAC 0.1400 and 0.1398, Factor IX 0.3454 and 0.3454, Cellulose 1.515 and 1.509, STMV 4.810 and 4.813) and end sooner by the build of their start (Cellulose 1.642 to 1.566 s, STMV 2.720 to 2.516 s). *Memory.* New on the device, counted by the store (`MDRT_PROFILE`): the members and the index of each tuple set and the identities and inverse of the order, 2.8 MB on JAC, 9.2 MB on Factor IX, 71.1 MB on Cellulose, and 152 MB on STMV, 6% to 10% of the incidence structures (42.6, 164.4, 696.3, and 2,211 MB); the renumbered members replace the copy of the members of the same size outside the deterministic mode. The host no longer holds the renumbered members, a copy of the identities for each set, or the 16 MiB in which rows were written: the peak resident memory of `mdir run` in mixed precision falls from 408 to 403 MB on JAC, 418 to 397 MB on Factor IX, 822 to 735 MB on Cellulose, and 1,559 to 1,340 MB on STMV. *Not changed.* The CPU target; the store's decisions; the frame evaluator's order; every number of a run. *Rejected:* a count, a prefix sum, and an atomic fill on the device at every start (the order within a row would then need a sort); a stable sort of the keys (particle, tuple, slot) at every start; kernels in the runtime library; the identities read back once for each value (simpler, 0.1 to 0.7 ms on Cellulose, but a copy). *Validated.* The claim directly on the host's code (`python-kept-tuples.test`: for tuples of 2, 3, and 4 with several tuples a particle, the row of a place in a new order is the row of its particle in the order of the files, its members relabeled, element for element). Under `MDRT_CHECK_KEPT_TUPLES`, which now also compares every structure built on the device with the host's build: the starts of the four systems of the suite in a Python simulation and runs of three segments of `mdir run` (30 structures built and 10 taken on JAC, Factor IX, and STMV, 27 and 9 on Cellulose), none different; the GPU tests of the store, activations, frames, memory, and failures. `mdir run` against `main` to the bit in the deterministic mode, three segments and three more continued: every dataset of the checkpoint (282,708, 1,090,884, 4,903,320, and 12,805,152 numbers on JAC, Factor IX, Cellulose, and STMV) and every row of the energies, in mixed and double precision, none different. compute-sanitizer on the GPU sequence of the store's test: `memcheck` 0 errors (61 s), `racecheck` 0 hazards (299 s), `initcheck` 0 errors (41 s, without the check, whose host copies read the unwritten ends of rows); the job held the device about 6.5 minutes. `kept-tuples.mlir` of the GPU lowering checks the calls and kernels and that nothing is copied.
