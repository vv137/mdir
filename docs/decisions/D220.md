# D220

Recorded 2026-10-07.

**A Python simulation exposes its state where its program keeps it as read-only DLPack views: `Simulation.view()` returns the positions, velocities, and forces of the last boundary of its activation in the order of the program and the types it stores, the input index of each row, and the host values of its tunables; the view and every managed tensor taken from it hold a lease, and while one is alive the operations that write or free the buffers are refused.** Issue #131, M2a item 6, first part; writable views are #136. A view needs an activation: before the first run or evaluation and after a failure `view()` raises `SimulationError`. Dtypes are the program's: state f64 in double and mixed precision; forces f32 in mixed precision, f64 in double precision and in the deterministic mixed mode (#102). Leases: `run`, `minimize`, `run(0, energy=True)`, updates of tunables, and `save_checkpoint` (D223, which ends the activation; #207) raise `SimulationError` while `Simulation.leases` is positive; reads (`state()`) are allowed. A lease holds the native simulation (`std::shared_ptr`), not a Python object, so a deleter may run on any thread without the GIL and a tensor keeps its storage (and the device blocks of the activation, which do not return to the pool) after `del sim`. `View.valid` compares a generation that every part, start, and end of an activation advances; a lease keeps it true. Protocol (DLPack Python specification): `max_version` of major 1 or more gives a `dltensor_versioned` capsule (version 1.1, read-only flag), otherwise the legacy `dltensor`; a capsule not taken releases its lease when destroyed, a taken one through the deleter, once. On a device the producer records an event on the runtime's stream and makes the consumer's stream wait (`None`/1 legacy, 2 per-thread, a handle, -1 none; 0 is a `ValueError`); `dl_device` of another device and `copy=True` raise `BufferError`. The device id is that of the runtime's context, an ordinal under `CUDA_VISIBLE_DEVICES` (`mdrtDeviceOrdinal`). Consumer work: the first part, end of an activation, or end of the simulation after device views were exported waits for all work of the CUDA context (`mdrtDeviceWaitAll`, `cuCtxSynchronize`), which covers consumer streams other than the one handed over; an event recorded on the consumer's stream at the deleter was not taken, since that stream may be another or destroyed by then. Writes through a read-only view are undefined and not detected. Validation (`python-dlpack*.test`): NumPy on the CPU and a ctypes reader of the capsule with the CUDA driver API on a GPU in the suite, PyTorch 2.11 on the CPU and a GPU (`REQUIRES: torch`, `-Dtorch_python`): pointer sharing, IDs and values against `state()` to the bit, dtypes, a non-default consumer stream, aliases, exactly-once release with and without the GIL, consumer work outstanding at the release (a run after it read the old values), blocked runs and updates, and blocks that no other simulation takes while a tensor lives.
