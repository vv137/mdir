# D177

Recorded 2026-10-04.

**The binary tarball of a release is built for manylinux_2_28 and needs no CUDA toolkit: it is built on the PyPA image of glibc 2.28 (`packaging/Dockerfile.manylinux`), links libstdc++ and libgcc statically, and carries the runtime, the OpenMP runtime, HDF5, cuFFT, and libdevice; without `CUDA_ROOT`, `CUDA_HOME`, or `CUDA_PATH` the kernels link the libdevice in `share/mdir/cuda`.** A binary built on the host (Ubuntu 22.04) needed GLIBC_2.35 and GLIBCXX_3.4.30 and the host's HDF5, and so did not run on RHEL 8 or Ubuntu 20.04, which clusters still run. The baseline is that of PEP 600's manylinux_2_28, the one Python wheels use, and `scripts/release/check-binary.sh` refuses a symbol of GLIBC newer than 2.28, any need of the system libstdc++ by MDIR's own binaries, and a library that is neither bundled nor allowed by that policy. cuFFT (`libcufft.so`) and libdevice (`libdevice.10.bc`) are redistributable under Attachment A of the CUDA EULA ("The following CUDA Toolkit files may be distributed with applications developed by you"; Linux: `libcufft.so`, `libdevice.10.bc`), which the tarball carries beside them; the GPU then needs only an NVIDIA driver that supports CUDA 13.0, the CUDA of the image. `CUDA_ROOT` still selects another toolkit. The release script builds the tarball in that image, checks it, and runs `mdir doctor` and the minimization of `examples/ala3` from the extracted tree, without `CUDA_ROOT`, on the CPU and on a GPU.
