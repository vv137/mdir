# D289

Recorded 2026-10-19.

**A field of features is an `!md.field` with a feature dimension: any number of components, `!md.field<@atoms, 16 x f64>`, and the representation of O(3) that they carry in the type, `!md.field<@atoms, irreps<4x0e + 4x1o>, f64>`, in e3nn's notation [[Geiger2022]](../references.md#geiger2022), blocks in the order written and, within a block, `mul_ir` (the copies of each irreducible representation together, e3nn's and MACE's layout; the default) or `ir_mul` (the copies of each component together, SchNetPack's PaiNN), with the components of e3nn 0.4's real spherical harmonics, $(x, y, z)$ for $l = 1$.** #377, step 3 ([ml4-ir.md](../ml4-ir.md), Section 3). *Ruled* (the maintainer on PR #441, 2026-10-19), against a type of its own, which every op that takes a field (the gathers and sums, the maps, `from_buffer`, storage, precision, and `md_dist`'s $G$ and $G^\mathsf T$) would have had to accept although none treats features otherwise than a field of $N$ components. A field of several components has a floating element type; the verifier checks $M \ge 1$, $0 \le l \le 8$, and $N = \sum M(2l+1)$; precision assignment keeps the representation. Two fields of the same $N$ and different irreps are different types, so a stage cannot take features of another layout without a conversion that says so. The buffers of fields with $N$ components are `memref<? x N x f64>`, which the storage and the lowerings already took.
