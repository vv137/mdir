# D214

Recorded 2026-10-07.

**The GPU modules of a program are serialized in parallel on the process's compile threads, their PTX and cubins are kept in the compile cache, and they are loaded as cubins compiled by the toolkit's `ptxas` for the architecture of the device that NVML reports. `MDIR_GPU_BINARY` (`auto`, `cubin`, `ptx`) and `MDIR_GPU_ARCH` choose otherwise.** Issue #148; the maintainer's decisions on PR #164.<br>*Pipeline.* `mdir-gpu-lower-to-nvvm` is upstream `gpu-lower-to-nvvm-pipeline` pass for pass, with its options and `binary`. Its `mdir-gpu-module-to-binary` serializes the `gpu.module` ops with `failableParallelForEach` on the context's pool (D211, `MDIR_COMPILE_THREADS`). It builds the symbol table before the threads start, puts the binaries back in module order on one thread, and drops upstream's per-object timing properties, so the lowered module is byte-identical from run to run and for any number of threads. `mdir run` now lowers on the same shared pool.<br>*Cache.* The PTX of a module is cached in `<MDIR_COMPILE_CACHE_DIR>/gpu/`, keyed by a BLAKE3 hash of its printed IR (generic form, nothing elided, no locations), its target attribute, the libdevice it links, the LLVM version, and `MDIR_GPU_BINARY`. The key holds no MDIR build identity: the module holds only upstream LLVM/NVVM ops. A module that refers to a `dense_resource` blob is not cached. The cubin is keyed by the hash of its PTX, `ptxas --version`, its arguments, and `MDIR_GPU_BINARY`. The entries use D212's format, atomic writes, checks, and eviction, and `MDIR_COMPILE_CACHE_MAX_MB` bounds the host and GPU entries together (least recently used first across both). `compile_stats` gains `gpu_*` keys.<br>*Cubins.* `ptxas` (upstream's arguments, `-arch sm_XY --opt-level 2`; at most 32 processes at once) is that of the toolkit whose libdevice is linked, else the one on `PATH`. `mdir.compile` now takes the same toolkit as the simulation. The architecture is `MDIR_GPU_ARCH`, else NVML's compute capability of the device that `Execution.device`/`MDRT_DEVICE` and `CUDA_VISIBLE_DEVICES` select (a UUID entry directly; an index only under `CUDA_DEVICE_ORDER=PCI_BUS_ID`, or when all devices agree), if LLVM knows it. The CUDA driver is not initialized at compile time, so a process may fork after `mdir.compile`. Fallback under `auto`: unknown architecture gives PTX for `sm_75` as before; no `ptxas` or a failing `ptxas` gives PTX for the architecture. Under `cubin` these are errors. `ptx` keeps PTX.<br>*Not chosen:* the nvPTXCompiler static library (58 MB per binary); `cuInit` at compile time (breaks a fork after compile); a fatbin with cubin and PTX (larger objects and host code generation).<br>*Evidence.* The dipeptide in water (PME, SHAKE, SETTLE, deterministic) through `mdir emit --stage=lowered`: byte-identical to main (main's timing properties stripped) at 1, 8, and 128 threads, cold and warm. The state after 20 steps through Python is bit-identical to main on the CPU (mixed, double) and the GPU (mixed, double) with the cache off, cold, and warm. The Python ala3 example (`--steps-scale 0.01`, deterministic, mixed, RTX 3090) writes main's energy files, DCD, and minimized positions byte for byte in every configuration. The whole example took 147.1 s on main with the driver's PTX cache warm and 188.6 s with it disabled. It took 82.5 s after the parallel serialization. With cubins it took 81.5 s with the compile cache off, and 59.7 s with it warm even with the driver's cache disabled; the JIT part of a stage fell from 1.7–6.2 s (5.6–18.8 s with the driver's cache disabled) to 0.3–0.5 s. CPU time, with the children: 216 s on main, 372 s with cubins and no cache, 136 s warm. The dipeptide's `Simulation(program)` took 15.7 s on main (21.0 s with the driver's cache disabled), 7.6 s with cubins, and 4.7 s warm. The full suite (one RTX 3090, 16 GPU workers) took 225 s with an empty suite cache and 150 s warm, against 250 and 243 s for D212. Production of ala3 under `mdir run` has 400 GPU modules of one kernel each, 292 distinct up to names (223 `tuple_for`), and the Python program of segments has 624; merging or deduplicating them is #167.
