# D215

Recorded 2026-10-07.

**A Python simulation runs every part in one activation of the entry of its program of segments, which waits at the end of each part on a stack of its own and hands the host its state where it is; its buffers, order of the particles, and neighbor structures persist from part to part, a run in parts equals one run to the bit in the deterministic mode, and the host copies the state only where it is asked for.** Issue #135, the base of #131 and #138. Amends D196, under which each part was a call that built its buffers, order, incidence structures, and neighbor structures anew from the state of the host and copied the state back (10.3 ms for a part of 10 steps of JAC against 2.7 ms of steps, 50 MB copied to the device per part), and #110/#115, whose allocations of a call become those of an activation. The program wraps its loops of steps in a loop over parts whose iteration begins with `mdrt.host_call @mdrtPartBoundary(x, v, f, id, not_numbers, part_counts) {in_place}`: `in_place` (new) hands the host the buffers of the fields where they are (`md-exec-assign-storage` casts the memory space; `md-exec-assign-precision` gives them no copy in the deterministic mode), and the host writes the step and counts of the next part. The entry keeps the buffers of the host as arguments, taken once when an activation begins; an entry that takes device buffers it does not allocate was rejected, since it would take out of the program the f32 and folded tables, the incidence structures, and the neighbor structures with their runtime handles, and the buffers rotate through the loops anyway. The runtimes record allocations per activation (`mdrtActivationOpen/Enter/Leave/Close`, `mdrtDeviceActivation...`, replacing `mdrtBeginCall`/`mdrtDeviceEndCall`), and so does the memory of the host that the code takes; an activation ends at a boundary (end of the simulation, failure, update of tunables, evaluation after the first run) by freeing what they list and unmapping its stack, never returning or unwinding. Failures: after each part that succeeds the state is copied on the device into memory the simulation holds, and a part whose count of components that are not numbers is not 0 (or that D107 or D142 stops) returns to that copy, or to the state of the host for a part that began an activation. Updates of tunables and evaluations after the first run copy the state, end the activation, and begin one from the host with `%first_call = 2`, keeping D213's equality with a compile from the same state. The CPU has the same ownership. Validation: runs in parts against one run, reporters, and minimization equal to the bit (CPU and GPU, double and mixed, deterministic); failures, updates, threads, and memory in `python-resident-*.test` and `python-memory*.test`. On one RTX 3090, parts of 1, 10, and 100 steps of JAC in mixed precision take 0.309, 2.75, and 27.2 ms instead of 8.77, 10.3, and 34.0; a long run is unchanged (0.272 against 0.275 ms per step, alternated).
