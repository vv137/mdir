# D234

Recorded 2026-10-08.

**The compile cache keeps the total of its entries in a file, `<dir>/size`, which a compile that stored entries updates under a lock of the file, and lists the directory to evict only when that total exceeds the bound, when no total is known, or when the last listing is a day old.** Issue #196. Before, every run of the GPU pass that stored an entry and every stored host object listed `host/` and `gpu/` and read the status of every entry (D212, D214), so a compile cost file operations in proportion to what the shared directory held: 13,268 statuses for the four stages of the ala3 example into an empty cache and 93,268 into one of 10,000 entries, which stalled suites whose build tree was on a network file system. A total kept only in the process was rejected: a process cannot know what the directory holds without a listing, so it would list once per process, and most processes compile one program. The lock is `fcntl`'s, which a network file system carries, with a mutex between threads; without a usable file every store lists, as before. The total is exact after a listing; afterwards it can only be too large (an entry replaced or removed by hand is still counted, which brings a listing sooner), except for the bytes of a process that died between its stores and its update, at most one program's entries, which the listing of the next day finds. `MDIR_COMPILE_CACHE_MAX_MB` keeps its meaning, a bound of 0 lists at every store and keeps nothing, and at the bound every store that exceeds it lists, as before; evicting below the bound to space the listings was left out, since it would change what the bound keeps. `mdir.clear_compile_cache` takes what it removes off the total.
