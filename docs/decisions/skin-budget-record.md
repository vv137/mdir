# D[skin-budget-record]

Recorded at its merge.

**The skin search keeps measuring its budget, records the budget and the candidates with the choice in the cache of the skins (format 2) and in the manifest, and a later run of the same key reuses the recorded choice instead of searching again; the key of that cache holds the salt of the compile cache (D397), so another build searches anew.** Issue #837, found in the review of #827; the maintainer's ruling: option 3, with the salt added.

*The problem.* The search (D281) affords $\min(7, \lfloor 0.02\,t_\text{run}/(t_\text{compile} + t_\text{steps})\rfloor)$ candidates of the reference's cost and searches only from 3. $t_\text{compile}$ is measured, and with the compile cache on by default (D397) a warm cache shortens it, so the same input could afford a search, or more candidates, on its second run and choose differently. The alternatives were a compile time that does not depend on the cache (the cold time recorded, or an estimate per module) and leaving the compile time out; the maintainer chose to keep the measurement and to record it.

*The record.* An entry of the cache now holds `format: 2`, the key, the chosen reaches, and `search`: `budget`, `budget_basis` (the policy, the share 0.02, the most 7, the estimated seconds of the run, the seconds of a candidate and of its compilation), the reason, the seconds, and the candidates, as the manifest gave them before. The manifest's `effective.skin_search` adds `searched` (whether this run searched), `budget`, `budget_basis`, `cache_refused`, and `not_cached`; where the choice was reused, its budget, basis, and candidates are those of the entry, with `recorded_reason` and `recorded_seconds`, and its `seconds` are 0. The log's line `MDIR: skins:` says `searched now: a budget of B, N candidates in S s` or `reused, not searched: the search of a budget of B recorded N candidates in S s`.

*Reuse.* The cache was already read before any search, so a run of the same key took the choice; what is new is that the record says what the choice was made from. A run whose budget falls below 3 still caches nothing, so that a longer run of the key may search; its manifest gives `budget` (for example 0), `budget_basis`, the reason, and `not_cached`. A warm compile cache can therefore still let a later run of a key search where an earlier, shorter one could not; once a choice is cached, it is reused.

*The key.* Its first line is `mdir skins 2` (it was `mdir skins 1`), and the build follows it (`getSkinSalt`, the maintainer's ruling on the PR: a fourth option between the full salt of D397 and one without the image). A clean build (the dirty flag `no`) is named by the version, commit, and dirty flag of MDIR, LLVM's version and revision, and the LLVM options of the command line, the lines of the salt of D397 without its `image` line, so that `mdir` and the Python extension of one clean build, two images, share a choice, as D281 describes. A dirty build, or one whose state is `unknown`, keeps the `image` line (the ELF build ID of the image that holds `lib/Compiler`), so that a development build with a changed kernel never reuses an earlier build's choice. The version of MDIR alone, as before, let such a build keep an earlier build's choice. Two clean builds of one commit with other compilers or build types share a choice; the choice changes the speed, not the forces. The device's name stays in the key (nodes of one model share a choice; no device UUID), and a cache on a network file system stays shared, written as a temporary file and renamed. `mdir check --json` gives the key as `run.skins.cache_key`, and `Program.plan["skin_cache_key"]` in Python.

*The reader.* An entry is taken whole or not at all. One that does not parse, has another `format` or none (format 1 had none), holds another key, lacks the chosen reaches, a `budget` of at least 3, its candidates (one to the budget), its reason, or its seconds, or whose chosen reaches are not among its candidates, is refused: the run goes on as without an entry, the log names the file and why, a search writes a new entry over it, and `mdir check` adds the note `skin_cache_refused`.

*For tests.* `MDIR_SKIN_SEARCH=budget` searches whatever the length, within the budget that the length affords, so a short run affords fewer than 3 candidates; `always` keeps the most. `MDIR_COMPILE_CACHE_SALT_OVERRIDE` is added to the key of the skins as to the salt; `MDIR_SKIN_SALT_DIRTY_OVERRIDE` stands for the dirty flag of the build. `test/Driver/skin-auto-gpu.test` checks the record, the reuse with a warm compile cache (the second run's candidates equal the first's to the bit), another salt, each refusal, and a budget of 0; `test/Driver/skin-salt.test` that the key of a clean build is the same for `mdir check` and Python and that of a dirty build is not, and that an LLVM option changes it; `test/Driver/compile-cache.test` (`composeSkinSalt`) that another commit, LLVM, or option changes the salt, and that the image is in it only for a build that is not clean.
