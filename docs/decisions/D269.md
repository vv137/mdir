# D269

Recorded 2026-10-16.

**The host code of a program takes LLVM's module pipeline at O3 before the code generator, in `mdir run` (a transformer of MLIR's `ExecutionEngine`) and in a simulation (`JITEngine`); the level is in the key of the compile cache, whose hash of the module is taken before the pipeline, so that a hit costs neither the pipeline nor the code generation.** Issue #359, step 1 of D267. Until now the code generator alone compiled the host code: no template helper was inlined (`mdrt.minimum_image` was three calls for each candidate of a search; the B-splines of PME were calls with their weights in stack arrays), and nothing was hoisted out of loops. *Measured* (alternated rounds in one job, the first dropped, mixed precision, `mdir run`, the compile cache off): on the CPU at 16 threads, JAC 19.30 ± 0.04 ms a step with the code generator alone, 16.30 ± 0.06 with O2 (−15.5%), 13.67 ± 0.04 with O3 (−29.2%) (EPYC 9354); TIP3P with 309,876 sites 341.7 ± 0.8, 284.5 ± 1.0 (−16.7%), and 252.5 ± 0.8 (−26.1%) (EPYC 7543). On an RTX 4090 the GPU programs, whose host code goes through the same engine, are unchanged: JAC 0.135, 0.135, 0.134 ms; TIP3P 103k 1.142, 1.140, 1.140 ms. The compile time of the host code grows by 1.6 to 1.8 s on the CPU (JAC 2.30 → 4.02 s with O3, 3.86 with O2; 103k 1.68 → 3.45) and by 0.8 to 0.9 s on a GPU (JAC 7.22 → 8.15 s). O3 takes 11 to 16% less time a step than O2 for 4 to 5% more compile time, so it is the level. *Results:* the pipeline keeps the floating-point semantics of the module (it neither contracts nor reassociates what the module does not allow): on the CPU the printed energies of every round agree to every digit; in the deterministic mode the state after 200 steps is the same to the bit on JAC on the CPU and on a GPU and on TIP3P 103k on a GPU, for the code generator alone, O2, and O3, and for two runs of O3.
