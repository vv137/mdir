# D212

Recorded 2026-10-07.

**A Python simulation's JIT engine takes its host object from an on-disk cache keyed by the content of its LLVM module and of the code generator, not by the build of MDIR; the cache is enabled by `MDIR_COMPILE_CACHE_DIR`, disabled by `MDIR_COMPILE_CACHE=off`, and bounded by `MDIR_COMPILE_CACHE_MAX_MB` (2048, least recently used first), and `Simulation.compile_stats` reports it.** Issue #142; the maintainer's decisions on PR #158. The relocatable object is a function of the module and the code generator alone, so the key is a BLAKE3 hash of the module's bitcode before code generation (which holds the PTX of the kernels and every constant of the program), the LLVM version, triple, CPU name and features, code generation level (D197), code and relocation models, data layout, the target options that change code, the pre-RA scheduler (D150), and a format tag: a rebuild of MDIR that generates the same module hits, one that changes generated code misses, and an object never crosses CPU features. The cache is the `llvm::ObjectCache` of ORC's `TMOwningSimpleCompiler` (as in LLVM's `LLJITWithObjectCache` example). An entry stores its full key, its length, a BLAKE3 hash, and the time of its generation; any mismatch or an object LLVM cannot parse is a miss and the entry is rewritten. Writes go to a unique temporary file and a rename, reads copy the file, and a hit touches its entry for the eviction. A hit only replaces code generation: each engine links and validates its own copy (D199 unchanged). The test suite shares `<build>/test/compile-cache` (`test/mdir_lit.py`, `-Dcompile_cache=off`). Not in this decision: `mdir run`, which still compiles with MLIR's `ExecutionEngine`, takes it with #99; a per-GPU-module cache keyed before PTX goes with #148; the MLIR pipeline, which depends on MDIR's passes, is not cached. *Evidence.* The dipeptide in water with PME, SHAKE, and SETTLE, deterministic, 20 steps, one process per scenario: a cold and a warm cache give the state of no cache bit for bit on the CPU and a GPU, in mixed and double precision (`compile-cache-{mixed,double}{,-gpu}.test`); a truncated entry and a flipped byte are rejected and rebuilt, a run that is not deterministic and one in the other precision miss, a bound of 0 MiB keeps nothing, and four processes at once on an empty directory leave one entry and agree with no cache (`compile-cache-mixed.test`); keys, damaged entries, and eviction in `compile-cache.test`; the D199 checks with a cold and a warm cache (`jit-memory.test`) and the lifetime tests with a cold and a warm suite directory. A rebuild of MDIR after changing one message in `lib/Compiler/Compile.cpp` hit on the CPU and a GPU with the same state; the engine took 0.09 s instead of 1.70 s on the CPU and 1.03 s instead of 3.09 s on a GPU. The Python ala3 example (RTX 3090, mixed, `--steps-scale 0.01`): 153.8 s with the cache off, 150.8 s cold, 140.6 s warm (the production stage misses: it starts from the cell the NPT stage reached), and 154.7 s cold and 137.3 s warm in the deterministic mode, where all four stages hit and the outputs equal those of the cold run byte for byte; the engine's part of a stage falls from 2–8 s to 0.8–2.0 s, and the MLIR pipeline remains most of the 12–54 s per stage. The full suite at the default `gpu_workers` (16), single runs on a shared host: 262 s off, 250 s cold, 243 s warm, within the noise of load; the GPU lifetime tests took about 163, 128, and 124 s and `python-reporters-gpu.test` 207, 198, and 188 s; 86 entries (139 MB).
