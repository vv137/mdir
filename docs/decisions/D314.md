# D314

Recorded 2026-10-21.

**The incidence structure of a tuple set is stored in ragged rows (CSR [[Saad2003]](../references.md#saad2003)): one buffer of i32 holding the number of rows $N$, the offsets $o_0 = 0 \le \dots \le o_N = M$ in entries, the $M$ entries of $a + 2$ values (the tuple, the place of the particle in it, its members), and one entry of zeros; row $i$ is the entries $o_i$ to $o_{i+1}$, $N + 2 + (a + 2)(M + 1)$ elements in all. The storage type of `!mdrt.incidence` is `memref<?xi32>`. Code reads a row only through one accessor (`include/mdir/Conversion/RaggedRows.h`: `emitRaggedRow`, `emitRaggedEntry`), which the templates of the neighbor builds call as the device primitives `ragged_row` and `ragged_entry`. On a device the structure is built from the members by the primitives of D296 (`emitDeviceRaggedRows`): a count of the memberships of each place with a device atomic, the device scan, a cursor scatter, and an insertion sort of each row; the index that the host built for each tuple set and uploaded (D257) is gone. The CPU takes the same layout.** #471, step 2 (the plan agreed on 2026-10-21). *Order within a row*: ascending membership number $a t + s$, which is ascending tuple and, within a tuple, ascending place, the order of the host's build (`mdrtTupleIndexBuild`) and of the dense rows before; the sort removes the order of the atomics, so the structure is the host's element for element in every mode, and `MDRT_CHECK_KEPT_TUPLES` compares whole buffers. *Reads past a row*: a kernel of an integration run reads the first entry of every row and keeps it only where the row has one (#347); that read is the next row's first entry or the entry of zeros. *Bound*: the offsets and tuple numbers are i32, so a set holds at most $2^{31} - 1$ memberships; the runtime refuses more (`mdrtTuplesSize`). *Trade-off*: a buffer of i32 of rank 1 has the type of an i32 field, so the ODS constraint of an incidence operand no longer tells them apart; two buffers would have added an operand to every op that takes the structure. *Validation* (RTX 4090; main d38d9eb6 and the branch in one job): in the deterministic mode the logs and the final checkpoints (positions, velocities, forces, box) bitwise identical to main on JAC (200 steps, mixed and double) and STMV from the GROMACS topology (100 steps mixed, 50 double); on the CPU, JAC 200 steps, mixed and double, bitwise identical; outside the deterministic mode the differences from main after 25 steps are those of main from run to run (RMS of the differences of the forces, main against the branch, main against main, the branch against the branch, kcal/mol/Å: JAC mixed 0.068, 0.066, 0.067; JAC double 1.20e-10, 1.21e-10, 1.22e-10; STMV mixed 0.267, 0.268, 0.266). *Measured* (`MDIR_DEVICE_MEMORY=2`, NPT 4 fs, mixed, groups, 1,000 steps, STMV from the GROMACS topology): its ten structures from 2,096 MiB to 228 MiB, the store of the tuples from 2,360 to 340 MiB of the driver's use; the device peak 5,641 → 3,663 MiB (×1), 15,717 → 9,833 (×3), 20,771 → 12,939 (×4); ×6 (6,402,570 atoms) runs in 19,147 MiB and ×7 (7,469,665) in 22,883 MiB, so the largest STMV replica on 24 GB goes from ×4 to ×7. Rates of the Amber suite (median of 3 rounds, ns/day, main → branch): JAC NVE 1276.8 → 1267.3 (time ×1.007), JAC NPT 1154.3 → 1156.3, JAC NVE 4 fs 2373.4 → 2363.1 (×1.004), JAC NPT 4 fs 2220.5 → 2236.4, Factor IX NVE 573.1 → 581.9, NPT 534.5 → 540.6, Cellulose NVE 150.1 → 153.7, NPT 142.5 → 146.2, STMV (the suite's prmtop) 88.1 → 91.6 (×0.962).
