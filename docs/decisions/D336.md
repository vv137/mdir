# D336

Recorded 2026-10-22.

**`mdir run` writes each checkpoint on a thread of its own while the steps go on: the call of the host copies the state as the program holds it and the rest of the file, and the thread orders the state into the order of the input, hashes it, and writes, synchronizes, and renames the file. The next checkpoint, a stop on a signal or the wall time, the end of the run, and the exit of the process wait for the write; a write that fails stops the run at the next wait, with its error and the status 1.** #548, parts B and C of its plan. Three events are kept apart (the maintainer's addendum of #574, Section 6): the copy from the device ends before the call, which copies into staging buffers that the write owns, so the program may overwrite its own buffers when the call returns; the thread releases the staging buffers once it has ordered them, and only it does; the commit (`.partial`, `fsync`, `.prev`, rename, `fsync` of the directory) follows. The next checkpoint waits for the release and the commit of the one before; a stop, the end of the run, and the exit wait for all three. There is one writer and one write at a time. The whole of `writeCheckpoint` runs on the thread, with the mutex of #262 around its part in the library alone, and the file has the same layout and values: `mdir checkpoint` finds the states of main's and the branch's files identical, and each continues the other. The hashes are computed before the library is entered. Without a periodic cell the call orders the positions itself, since their spread may stop the run (D142). The Python simulation's `save_checkpoint` still writes in its call. The stop on the wall time waits for its write, which the interval between checkpoints no longer holds (under a second on STMV). C of the plan, the order on the device and an asynchronous copy into pinned memory, was not done: what remains on the path of the steps on STMV is 6.0 ms of copy from the device, 11.1 ms of copy of the state, and 3.2 ms of the rest, 0.5% of the window of 1000 steps, and its form is a question for #567 (the copies of the host and the device ordered by tokens). *Evidence.* `checkpoint-write-failure.test` (a directory that cannot be written: the rows go on past the failed checkpoint and the run stops at the next one, or at its end, with the error and the status 1, where main stopped at the failed one), `checkpoint-staging.test` (each write held back by 300 ms, so that the next checkpoint is requested while the write before still holds its staging buffers: it waits for it, and both checkpoints and the rows equal those of a run whose writes are not held back, bit for bit). In the deterministic mode on one RTX 4090, JAC NPT in mixed and double precision (2000 steps, a checkpoint at 1000) and STMV NPT ×1 in mixed (200 steps, at 100): the run that goes on, of the branch and of main, and the run stopped at its checkpoint and continued, branch then branch, main then branch, and branch then main, have the same final checkpoints, the same checkpoints at the stop, and the same rows after it, bit for bit (36 of 36 comparisons). The CPU tests that write checkpoints (95) and the GPU tests (70), the Python checkpoint tests among them, pass. *Measured* (one RTX 4090, the suite's output, default reaches, alternated with main in one job, three repeats): STMV 88.04 ± 0.08 ns/day against 81.07 ± 0.09, the output's share 0.99 ± 0.30% against 8.83 ± 0.22% (energies alone 88.92 ± 0.20); Cellulose NVE 146.79 ± 0.12 against 144.70 ± 0.16, share −0.33 ± 0.27% against 1.10 ± 0.25%; Cellulose NPT 139.60 ± 0.19 against 137.55 ± 0.18, share −0.94 ± 0.21% against 0.55 ± 0.19%. A share below zero is the new order of each segment (D335), which the run with the energies alone, one segment, does not have. The steps waited 0.0 ms for every write; on its thread a write took 352 ms on STMV and 137 ms on Cellulose. The peak resident memory of the process rose from 1552 to 1615 MB on STMV and from 964 to 992 MB and 1051 to 1082 MB on Cellulose: the staging buffers and the ordered state of one checkpoint. No control-file key, file format, or overwrite behavior changes.
