# D155

Recorded 2026-10-03.

**The README begins with a runnable quickstart, and `mdir doctor` checks an installation by compiling and running an embedded system on each built target.** U8: a build's version and toolkit path do not show whether its JIT, runtime, OpenMP library, CUDA driver, or device work. The doctor reports the build and dynamically probes the CUDA driver for its supported API version and visible devices, respecting `CUDA_VISIBLE_DEVICES` and `MDRT_DEVICE`; it needs no linked driver to diagnose a missing one. Each target runs a two-atom Lennard-Jones system for two steps in a child process of the same executable, with a 120-second timeout, double precision and two threads on CPU, mixed precision on GPU. Success requires the initial potential energy to agree with its analytic expression within the log's rounding and both energy rows to be finite. Child processes isolate JIT or runtime failures so the other target can still be checked. Inputs, captured logs, and compiler reproducers stay in a unique temporary directory on failure, with paths and a rerun command; success removes them. The default checks all built targets, skipping an unbuilt GPU; an explicit unavailable GPU or a CUDA build without a working device fails. `--target=cpu` makes a CPU-only check explicit. Actual CUDA build availability, rather than a possibly stale toolkit path, also controls `version` and preflight. The fixture is embedded so an installation needs no source checkout, and writes no checkpoint so HDF5 is optional; HDF5 support is reported, not exercised. This is a check of basic execution, not of PME, constraints, or a user's system. Tests cover successful CPU and GPU runs, invalid targets, retained failure diagnostics and reproducers, cleanup, and unavailable or invalid device selection.
