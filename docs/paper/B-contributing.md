# Appendix B. Taking part

## B.1 Building and testing

MDIR needs a C++17 compiler, CMake 3.20 or later, Ninja, LLVM and MLIR
23.1.2 (`scripts/build-llvm.sh` builds them with the X86, NVPTX, and AMDGPU
targets and the OpenMP runtime), `lit`, and, for NVIDIA GPUs, the driver
and a CUDA toolkit for its headers and device math library. HDF5
(`scripts/build-hdf5.sh`) enables checkpoints.

```sh
cmake -G Ninja -S . -B build -DCMAKE_BUILD_TYPE=Release \
    -DLLVM_ENABLE_ASSERTIONS=ON \
    -DMLIR_DIR=$LLVM_PREFIX/lib/cmake/mlir -DLLVM_DIR=$LLVM_PREFIX/lib/cmake/llvm \
    -DLLVM_EXTERNAL_LIT=$(command -v lit) -DHDF5_ROOT=$HDF5_PREFIX
cmake --build build --target check-mdir
cmake --install build --prefix $PREFIX
```

The installation is `$PREFIX/bin/mdir` with its runtime, the GPU runtime,
and the OpenMP runtime of the LLVM build in `$PREFIX/lib`; its RPATH holds
`$ORIGIN/../lib` and the directories of the libraries it linked, such as
HDF5, so it runs without the build trees of MDIR and LLVM.
`packaging/` builds the same installation in a Docker or an Apptainer
image, on CUDA's runtime image with libdevice from the toolkit.

*Table B.1. Tiers of tests.*

| Tier | How | What |
|---|---|---|
| Default | `lit test` | Dialects and passes (`test/Dialect`), lowerings (`test/Conversion`), templates (`test/Runtime`), generated code run on the host (`test/Integration`), and runs of the driver on the CPU and the GPU (`test/Driver`) |
| Sanitizer | `lit -Dsanitize=1 test` | The GPU tests under compute-sanitizer |
| Release | `lit -Drelease=1 test` | The whole matrix of the tests that run a part of their cases by default (`*-release.test`, `*-release-gpu.test`); the suite of `scripts/release/publish.sh` |
| Scale | `MDIR_BENCH_DIR=<dir> lit test/Scale` | Short runs of the Amber benchmark suite |
| Host sanitizers | `scripts/build-sanitized.sh <dir>` | All tests with the driver and runtimes under AddressSanitizer and UndefinedBehaviorSanitizer |

The Python `observe` tests use Double with cutoff and Mixed with shift
for the dipeptide and Double with shift and Mixed with cutoff for the
mixture in the default CPU and GPU tier. Their release twins test the
full precision and modifier matrix with the same independent CLI file
oracles and closed-form dispersion checks (D324, #530). Both
tiers keep the NPT checks in Double and Mixed precision.

Where two GPU allocations are available, the default tier can run as two
lit shards on independent build trees of one commit (D309), in the
lexical order of the tests (D344). Both
shards must pass; their disjoint selections together contain every default
test. This changes elapsed validation time and uses two allocations, not the
tests or the numerical oracle.

A test that writes outputs puts them under its own `%t` and removes it
first, `rm -rf %t && mkdir -p %t` on its first line: `mdir` keeps an output
that exists as a numbered backup and stops after 99 of them, so a test that
wrote at fixed paths failed after 99 runs of the suite in one build tree
(#423). `test/Lit/test-outputs.test` lists the tests that do not.

## B.2 Where a change goes

| Directory | Contents |
|---|---|
| `include/mdir/Dialect/{MD,Dyn,MDExec,MDRT}`, `lib/Dialect/...` | The dialects: types and ops in TableGen, verifiers, and the passes over `md` and `md_exec` (`lib/Dialect/MDExec/Transforms`) |
| `lib/Conversion/MDToMDExec` | From the semantic dialects to loops |
| `lib/Conversion/MDExecToLoops`, `lib/Conversion/MDExecToGPU` | The lowerings to `scf` (CPU, with OpenMP) and to kernels of the `gpu` dialect |
| `lib/Conversion/MDExecKernels` | What one thread of a loop does, shared by both lowerings |
| `lib/Runtime/Templates` | Templates in MLIR: the builds of neighbor structures, PME on a device; some are generated by scripts in `scripts/` |
| `runtime/` | The runtime in C: the pool of device memory, the stream, flags, the buffers of neighbor structures, the log, random numbers, the barostat and thermostat factors |
| `lib/Driver`, `tools/mdir` | The control file, the readers of topologies, the builder of the program of a run, checkpoints, and the command `mdir` |
| `examples/` | Tutorials, each the stages of the standard pipeline as control files (minimization, equilibration at constant volume, at constant pressure with restraints, production): tri-alanine and ubiquitin in OPC, and a POPC bilayer in TIP3P; and argon, a Lennard-Jones fluid run from its IR |
| `scripts/validation`, `scripts/benchmarks`, `scripts/render` | The comparisons with other programs (Section 9), the measurements of Section 10, and movies of trajectories |

**A new term of the potential** is a function of the builder
(`lib/Driver/BuilderPotential.cpp`) that writes an `md.potential` term over a
relation, with its parameters as fields of the tuple set; its forces and
virial follow by differentiation. If the term is a pair term with an
exchange contract, it runs over groups on a device with no further work.
The migrated kinds instead implement `TermBuilder` in a translation unit
of their own and are listed explicitly in `lib/Driver/TermBuilders.cpp`
(D359). External terms are the first: their fields, potentials,
energy-output names, and observable lookup live in `TermExternal.cpp`.
Their entry buffers still follow the shared field list. Every migration
keeps the printed module and lowered program byte-identical to main over
the builder-equivalence corpus; other kinds follow in separate PRs.

**A new pass** has its description and options in
`include/mdir/Dialect/MDExec/Transforms/Passes.td`, its code in
`lib/Dialect/MDExec/Transforms`, a test of its IR in
`test/Dialect/MDExec/Transforms`, and a place in the pipeline that
`tools/mdir/Run.cpp` builds (`mdir emit --stage=pipeline` prints it).

**A new optimization** has a switch, a test that compares the results with
and without it, and, if it reorders or overlaps work, an argument in its
decision (Section 12).

## B.3 Tools of diagnosis

| Tool | What it does |
|---|---|
| `mdir doctor [--target=all\|cpu\|gpu] [--timeout=<seconds>]` | Reports the build, probes the CUDA driver and visible devices, and compiles and runs a small system on the requested targets, each run within the limit (120 s by default; D155, #663) |
| `mdir check FILE [--json]` | Validates the input and reports the system, planned run, outputs, and warnings, without compiling or writing files (D151) |
| `mdir template amber`, `mdir template md` | Prints a control file with every keyword and its default |
| `mdir template minimize`, `nvt`, `npt`, `production` | Prints a stage of the standard pipeline, embedded at build time from `examples/ala3` (D147) |
| `mdir emit FILE --stage=STAGE` | Prints the program of a run as the driver built it (`module`), as lowered (`lowered`), or the passes (`pipeline`) |
| `MDIR_PRINT_AFTER=<pass>` | Prints the module after each run of that pass |
| `MDIR_PIPELINE=<passes>` | Replaces the pipeline, for example to turn one option off |
| `mdir-opt --run-reproducer mdir-reproducer.mlir` | Repeats a failure of a pass from the file that `mdir run` writes |
| `MDRT_WAIT=1`, `MDRT_TRACE=1`, `MDRT_PROFILE=1` | Waits after every launch and names the kernel that fails; prints modules, kernels, and launches; times each kernel |
| `mdir bug-report FILE -o DIR [--run]` | Collects the build, the machine, the inputs with their hashes, and every stage of the compilation into one directory for a report |

Kernels are named `<function>_<op>[_<kind>]_<n>`, where `<n>` is the
ordinal of the kernel in the lowering, so a profile or a report of the
sanitizer points at the IR (`MDIR_PRINT_AFTER=gpu-kernel-outlining` prints
the kernels in that order), and a name does not change with the text the
program was built from (D354).

## B.4 How a change is recorded and reviewed

A choice that changes a method, a structure, or a default is recorded as a
decision in `docs/decisions.md`: what was decided, why, and the
measurement before and after. The documents of the design
(`docs/*.md`) describe what is implemented and are updated with the code,
and so is this paper: a change to a method, an algorithm, or an
implementation updates the sections that describe it, their equations,
numbers, and tables, in the same piece of work.
Comments cite methods by the keys of `docs/references.md`, whose entries
are checked against their DOIs (`scripts/paper/verify-references.py`).
A review asks the questions of the checklist of `docs/principles.md`: what
the change assumes about its input and whether the IR states it; whether it
reuses, aliases, or reorders buffers, under what condition, checked where;
whether it can be turned off and is compared both ways; whether it depends
on sizes that the small tests do not vary; and whether a numerical method
is tested on its hard case.

The process around a change is described in `docs/workflow.md`. A change
lives on a branch of its own and opens a draft pull request as soon as its
user-visible design is decided, so that the design can be redirected
early. Its decision carries a label until the merge gives it a number in
the order of the merges. A reviewer runs the full suite on a GPU and
reports the result on the pull request before the maintainer approves the
merge.

D359's explicit term registry and the bounded interfaces of D361 now cover
all kinds of #683: externals, pulls, restraints, generalized Born together
with surface, custom tuple/centroid/compound terms, custom pairs, triplets,
staged/opaque models, every bonded family, and nonbonded terms. The bonded
families are bonds, angles, dihedrals, Urey–Bradley, harmonic impropers,
special 1–4 pairs, and CMAP. Nonbonded owns primary, excluded, reciprocal,
and within-selection LJ/Coulomb contributions and mesh/correction preparation.

Each build owns the adapter instances returned by the explicit factory list
(D[builder-term-roles]). The list retains static-link reachability. Adapters
borrow physical inputs, named parameter collections, streams, and shared
emission services; none receives the complete builder/program or scheduling
state. Born radii stay private to the combined Born/surface adapter. Imported
model bodies, result names, and cutoff metadata stay private to the model
adapter. The nonbonded role receives an explicit projection of mesh and
correction data, excluding entry and scheduling state.

The hook inventory and implementers are listed in driver Section 2.12.
Generic behavioral hooks have multiple active implementers. Separate table
and tuple refill hooks are folded into one shared array hook; independent
potential declarations and energy columns use one ordered definition record.
Restraint corrections, coordinate reporting, and custom-pair scalar operations
use narrow roles. Dispersion and gradient-shift hooks serve both custom pairs
and built-in nonbonded terms. The shared centroid emitter remains available
to pulls, and ordinary/special 1–4 LJ pairs share a scalar emitter.

Explicit ranks retain field, table, tuple, contribution, declaration, and
output order. Every term remains at the same shared/inlined potential site,
so kernel fusion and SSA names stay unchanged. The migration changes no
control key, numerical method, or format. Each kind commit compares its
printed module/lowered corpus and combined-kind order matrix with one fixed
archived PR base; the final head also compares five checkpoints bitwise and
runs two full-suite shards. The remaining #568 stages replace term templates
with typed `OpBuilder` IR and retain parsed text only for user expressions
and `ModelTerm` at their boundaries.
